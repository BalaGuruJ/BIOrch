# BIOrch LLM Planner & Adaptive Planning Contract

**Contract ID:** BIORCH-PLANNER-001  
**Contract Name:** LLM Planner & Adaptive Planning Contract  
**Phase:** Phase 10 — LLM-Based Adaptive Planning  
**Status:** DRAFT  
**Depends On:**  
- BIORCH-ORCH-001 — Deterministic Orchestrator Contract  
- BIORCH-RESOLVER-001 — Static AgentResolver Contract  
- BIORCH-TG-001 — Tool Gateway Contract  
- BIORCH-AGENT-001 — Deterministic Agent Contract  

---

## 1. Purpose

This contract defines the authoritative architectural boundary, behavioural requirements, and validation rules for **Phase 10 (LLM-Based Adaptive Planning)** within BIOrch.

Phase 10 introduces the capability for BIOrch to accept high-level natural language user intents and dynamically synthesize structured, executable `Workflow` graphs. This contract specifies how user intents are translated into intermediate `CandidatePlan` structures, compiled deterministically via the `PlanCompiler`, validated against security and structural invariants, and executed by the existing `DeterministicOrchestrator` and Phase 09 `Reviewer` loops.

---

## 2. Architectural Position & Pipeline Flow

The canonical pipeline for adaptive planning, compilation, validation, and execution is:

```
[User Intent (Natural Language)]
             ↓
    [LLM Planner Component]
             ↓
    [CandidatePlan (Intermediate JSON/Dict Representation)]
             ↓
    [PlanCompiler (Deterministic Compilation)]
             ↓
    [Canonical Workflow & Task Instances]
             ↓
    [Deterministic Plan Validator] (Schema, Dependency & Security Check)
             ↓  (Valid)
    [DeterministicOrchestrator] (Sequential / Parallel Execution + Phase 09 Review Loop)
             ↓
    [Synthesis & Provenance Validation]
```

1. **Intent Formulation:** The user provides a natural language objective (e.g., *"Inspect Power BI semantic model relationships and extract Tableau data lineage"*).
2. **Plan Generation:** The LLM Planner queries an abstract LLM provider with available agent capabilities and tool schemas to generate a structured `CandidatePlan`.
3. **Deterministic Compilation:** The `PlanCompiler` translates the `CandidatePlan` into canonical BIOrch `Workflow` and `Task` objects without mutating execution semantics.
4. **Mandatory Validation:** The workflow passes through strict schema, dependency, and security validation.
5. **Execution & Review:** Validated workflows are executed by the `DeterministicOrchestrator` and inspected by Phase 09 review loops.

---

## 3. Planner Responsibilities & Prohibited Responsibilities

### 3.1 Core Responsibilities (In Scope)
- Parsing and structuring natural language user intents into `CandidatePlan` representations.
- Managing interactions with pluggable `LLMProvider` backends (supporting API clients, local models, and mock providers).
- Injecting planning provenance and task-level rationales into metadata.
- Interfacing with the `PlanCompiler` to convert candidate plans into canonical workflows.

### 3.2 Prohibited Responsibilities (Strictly Out of Scope)
- **Direct Execution:** The LLM Planner MUST NOT execute tasks, invoke tools, or interact with the `ToolGateway` directly.
- **Bypassing Security:** The planner MUST NOT attempt to override agent allowlists or tool access restrictions.
- **Runtime Mutation:** The planner MUST NOT make policy, retry, or fallback decisions during workflow execution.
- **Modifying Core Infrastructure:** The planner MUST NOT alter `DeterministicOrchestrator`, `AgentResolver`, or `ToolGateway` runtimes.

---

## 4. CandidatePlan Structure & Purpose

The `CandidatePlan` is the intermediate, probabilistic artifact generated by the LLM Planner before deterministic compilation. 

A `CandidatePlan` MUST define:
- `plan_id`: Unique identifier for the planning session.
- `intent`: The original natural language user prompt or goal.
- `target_model`: The LLM identifier used for generation.
- `tasks`: An ordered list of planned task steps, where each step includes:
  - `task_id`: Unique task identifier within the plan.
  - `objective`: Non-empty string defining the goal or instruction for the agent, mapped 1:1 to canonical `Task.objective`.
  - `agent_id`: Target agent identifier.
  - `operation`: Requested operation name.
  - `inputs`: Dictionary of parameters and tool identifiers (`tool_id`).
  - `dependencies`: List of preceding `task_id`s upon which this task depends.
  - `rationale`: Explanation or reasoning provided by the LLM for why this task was generated.

---

## 5. Deterministic Compilation (`PlanCompiler`)

The `PlanCompiler` is a pure, deterministic component responsible for translating a valid `CandidatePlan` into BIOrch's canonical core models:
- **`Workflow`**: Contains `workflow_id`, `version`, and `tasks` (`List[Task]`).
- **`Task`**: Contains `task_id`, `objective`, `agent_id`, `inputs`, `dependencies`, and `metadata`.

### Compilation Rules:
- The compiler MUST perform a 1:1 mapping of candidate tasks to canonical `Task` instances.
- The compiler MUST explicitly map the `CandidatePlan` task `objective` 1:1 to the required canonical `Task.objective` (satisfying `schemas/task.schema.json`).
- The `objective` MUST be a non-empty string and MUST NOT be synthesized, inferred, or otherwise transformed by the `PlanCompiler`. The compiler MUST fail closed if `objective` is missing, empty, or not explicitly provided.
- The compiler MUST keep `rationale` separate as planner rationale (`task.metadata["planner_rationale"]`).
- The compiler MUST inject planning metadata (`workflow.current_state["planner"]` and `task.metadata["planner_rationale"]`) without altering functional execution parameters.
- The compiler MUST NOT introduce implicit tasks, auto-correct malformed step parameters, or guess missing agent assignments.

---

## 6. Mandatory Validation Before Execution

Before any LLM-generated workflow can be executed, it MUST pass mandatory validation enforced by the orchestrator:

1. **Schema Validation:** Verifies that required fields (`workflow_id`, `version`, `tasks`) and task attributes (`task_id`, `objective`, `agent_id`, `inputs`) are present and correctly typed against core schemas (`schemas/workflow.schema.json` and `schemas/task.schema.json`).
2. **Dependency Graph Integrity:** Validates that:
   - All `dependencies` reference existing preceding `task_id`s.
   - The task dependency graph forms a valid Directed Acyclic Graph (DAG) with no circular references.
3. **Agent & Tool Allowance Check:** 
   - Verifies every task's `agent_id` against the `AgentResolver` (BIORCH-RESOLVER-001).
   - Verifies every requested `tool_id` and `operation` against the target agent's immutable `ToolGateway` allowlist (BIORCH-TG-001).

---

## 7. AgentResolver & ToolGateway Authority

The introduction of LLM planning in no way relaxes existing security boundaries:
- **`AgentResolver` (BIORCH-RESOLVER-001):** Remains the sole static registry mapping `agent_id` to pre-initialized agent executors. Dynamic agent discovery or runtime registration by the LLM Planner is strictly prohibited.
- **`ToolGateway` (BIORCH-TG-001):** Remains the absolute authorization gate for tool access. If an LLM-generated plan proposes an unallowlisted tool or unauthorized operation, validation fails immediately.

---

## 8. Failure & Rejection Semantics

- **Planning Failure:** If the LLM provider fails, times out, or produces unparseable JSON output that cannot form a valid `CandidatePlan`, the planner MUST raise a deterministic `PlanGenerationError`.
- **Validation Rejection:** If a compiled workflow fails schema, dependency, or security checks, validation MUST reject the workflow (`WorkflowResultStatus.REJECTED`).
- **Fail-Closed Principle:** The system MUST NOT attempt heuristic auto-correction or "best-effort" execution of insecure or malformed plans. Rejection is terminal for that planning run.

---

## 9. LLM-Provider Abstraction Boundary

- **`LLMProvider` Interface:** All LLM communication is decoupled from orchestration logic via an abstract `LLMProvider` interface.
- Concrete implementations (e.g., Vertex AI Gemini clients, local testing stubs, or mock providers) implement this interface to return raw candidate text or structured JSON.
- Orchestration code depends solely on the abstract interface, ensuring modularity and testability.

---

## 10. Deterministic Mock & Provider Testing Requirements

- The LLM Planner architecture MUST support a deterministic mock provider mode.
- In mock mode, the planner returns pre-recorded or statically generated `CandidatePlan` fixtures corresponding to test scenarios.
- This enables robust, offline, non-flaky unit testing of planning, compilation, validation, and execution pipelines.

---

## 11. Planning Provenance & Audit Metadata

Every LLM-generated workflow and its constituent tasks MUST retain full provenance in their workflow state (`workflow.current_state`) and task metadata (`task.metadata`) dictionaries:
- `workflow.current_state["planner"]`: Dictionary containing:
  - `planner_id`: Identifier of the planner component.
  - `model`: LLM model identifier.
  - `timestamp`: ISO-8601 generation timestamp.
  - `intent`: Original natural language user prompt.
- `task.metadata["planner_rationale"]`: String containing the LLM's rationale for generating the specific task step.
- These metadata fields flow transparently through `ProvenanceValidator` (Phase 08.4H) without disrupting cryptographic SHA-256 checksum verification.

---

## 12. Backward Compatibility with Phases 01–09

- All existing static workflow definitions, direct orchestrations (Phase 04), parallel dispatches (Phase 08), and review loops (Phase 09) remain fully operational and unmodified.
- The LLM Planner is an optional, additive entry point situated strictly upstream of the orchestrator.
- Existing unit tests, schema definitions, and contract interfaces (BIORCH-ORCH-001, BIORCH-RESOLVER-001, BIORCH-TG-001, BIORCH-SYNTH-001) are preserved without modification.

---

## 13. Contract Invariants & Acceptance Criteria

1. **Separation of Concerns:** The LLM Planner plans; the `PlanCompiler` compiles; the Validator inspects; the `DeterministicOrchestrator` executes.
2. **Fail-Closed Security:** Unverified, unallowlisted, or malformed plans are rejected prior to execution.
3. **Authoritative Boundaries:** `AgentResolver` and `ToolGateway` authorities remain absolute and inviolable.
4. **Provenance Integrity:** Planning rationale and model metadata are successfully captured and preserved through execution and synthesis.
5. **Additive Architecture:** No existing contracts, schemas, source modules, or tests are modified by Phase 10 planning additions.
